## The concrete ground of the FAIL, as far as the code fixes it

`cleanup_checks` sets `.b` to FAIL when the list `leftovers` is not empty. A live process is put there by `from_job`, through one of three rules. Which one fired for PID 972 is **not recorded in the log**:

1. PID 972 was a job PID and its creation time equals one Windows confirmed inside the job (`peak_created`): a process of the job, still alive.
2. PID 972 was a job PID with no creation time recorded for it, the process was created between the start of the run and the end of the job (compared to the second), and its parent is a job PID or the harness itself.
3. PID 972 was not a job PID, but walking up its parents reached a job process, or a parent PID that is a job PID and is no longer alive (or was reused by a younger process).

Each rule needs a different fact about the parent and about the job's PID list. None of those facts is in the log.

## What can be said and what cannot

- **Seen:** a `powershell.exe` created 3 minutes 9 seconds after the step began and 2 minutes 54 seconds before the test run ended was alive when the harness took its process list after case T6, and the harness classed it as a leftover of the job.
- **Not seen:** its parent, its command line, whether PID 972 was in the job's PID list, whether a creation time was recorded for it, when the job ended.
- **Two readings that fit what is seen, neither proven:**
  - a real leftover: the case launcher (`launch_case.ps1`) is a PowerShell script, so the job does start `powershell.exe`;
  - the harness's own helper: `processes()` takes the process list by starting `powershell.exe` under the harness, and that process is alive, with the harness as its parent, in the very list it produces. Under rule 2 it would be called a leftover if its PID had been a job PID earlier and it started in the same second in which the job ended. That is a way the check could be wrong; whether it happened here is unknown.

## What was changed, and what was not

- **Changed (diagnosis only):** when `.b` has leftovers, the check now carries `why`: for each one its parent PID, the parent's name and creation time when the parent is alive, whether the parent is a job PID or the harness, whether the process's own PID is a job PID, the creation times recorded for that PID, the start of the run, the end of the job, the harness PID, and which of the three rules fired. `assert_no_fail` prints it with the failing check. Which processes are leftovers, and every status, are exactly as before. One new test covers it.
- **Not changed:** the rule itself. Changing it on a guess would hide the next occurrence instead of explaining it.
- **Not done:** no rerun of the failed job was started to turn it green. The red run stays in the history as it is.

## After GPT's review of 08.10.2026: the whole chain, and the attempt kept

The first diagnosis named only the direct parent, while `from_job` may walk several ancestors before it decides. Two additions, still diagnosis only:

- `why` now carries `parent_chain`: every link the walk took, up to where it stopped, each with its pid, whether it is alive, its name and creation time, whether it is a job pid or the harness, the creation times recorded for it, how the check judged it, and whether it is younger than its child (a reused pid).
- When `TRIAL_DIAGNOSTICS_DIR` is set, a failed `.b` writes one JSON file: the check with `why`, `proc_before` and `proc_after` (pid, parent, name, creation time, the reduced kind; command lines are never in these lists), the job's pids and recorded creation times, the start of the run, the end of the job and the harness pid. The CI workflow sets that folder for the two harness steps of the Windows job and uploads it as the artifact `trial-diagnostics` when a step fails (kept 30 days).

Tested: `test_a_leftover_carries_the_whole_chain_and_the_attempt_is_kept_for_ci`. Not tried on a hosted runner: the upload step runs only when a step fails, and no run has failed since.

## Open

The cause. It can be closed only by an occurrence that carries `why`, or by reproducing it on a Windows machine where the attempt folder can be read.
