# Trial harness, check `.b` red on `main` on the hosted Windows runner, 09.10.2026: cause established and fixed

Second occurrence of the red check described in `FLAKE_T6_6b_20261008.md`. That note ends: "the check now records both, so the next occurrence can be read". This is the next occurrence, and it could be read.

**Result in one line: the harness reported its own process lister as a leftover of the job, because the chain of parents was followed up to `wininit.exe`, whose long-dead parent's pid number had been given by Windows to a process of the job. Fixed in `run_trial.py`; a regression test carries this run's numbers and fails on the code as it was.**

## The chain of parents, as the check printed it

`powershell.exe` 9136 → `python.exe` 8080 (the harness) → `pwsh.exe` 3420 → `Runner.Worker.exe` 7392 → `Runner.Listener.exe` 3156 → `hosted-compute-agent` 6884 → `svchost.exe` 2544 → `services.exe` 972 → `wininit.exe` 856 (created `00:39:05.042`, with the machine) → **pid 740: not alive, `is_a_job_pid: True`, creation time recorded for it inside the job: `00:49:49.445103`**.

Every process in the chain is alive, none is a job pid and none is younger than its child, so the walk went on to the top. `wininit.exe` still names as its parent a process that ended at boot. Windows had since given that number, 740, to one of the 19 processes of the job. The code asked only "is the parent's pid a job pid?" (`return up in peak`) and answered yes.

So the process was created **one second after the job had ended**, by the harness itself (it is the PowerShell that takes the list of processes), and was attributed to the job through a pid number that belonged to two different processes ten minutes apart.

## What this proves, and what it does not

- Proved for this run: which rule fired, the whole chain, and that the job process under pid 740 (created `00:49:49`) cannot be the parent of `wininit.exe` (created `00:39:05`): a parent is created before its child.
- Reproduced: a test with these numbers fails on `run_trial.py` as it is on `main` with the same result (`FAIL`, PID 9136 `powershell.exe`) and passes on the fixed file.
- **Not proved: that the red run of 08.10.2026 (`T6.6.b`, PID 972 `powershell.exe`) had the same cause.** That run kept neither the parent nor the rule. The same mechanism would explain it, and it is not claimed.
- Not closed by a rerun: the failed run was not rerun.

## The fix

`from_job` in `run_trial.py`: when the parent of a process is gone (or its pid is held by a younger process), the pid number alone no longer decides. `gone_parent_was_in_the_job` says no when

- the child was created before the run began (a job process is created during the run, and a parent before its child), or
- Windows confirmed creation times for that job pid and all of them are later than the child's.

What neither rule settles stays as before: the pid number decides, so a real orphan of the job is still reported.

Test: `test_trial_harness.FalsePass.test_a_dead_ancestor_whose_pid_a_job_process_took_later_does_not_make_the_whole_machine_a_leftover` (this run's chain and times; the same without a recorded creation time; an orphan of the job that must still FAIL; a child older than every job process under its dead parent's pid). 74 tests pass on Windows (Python 3.12.10), 09.10.2026.
